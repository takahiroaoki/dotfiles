# Readability Review Checklist

根本原則は、行数ではなく読み手が理解に到達するまでの時間（Time-till-understanding）を最小化すること。各項目は対象コードに実際に当てはめ、既存規約・言語イディオムを先に優先する。

## 1. 命名と表面的な改善

- [ ] **確認観点**: 名前から役割、単位、状態、境界、入出力の向きが分かるか。スコープの広さに見合う情報量か。関連コードの整形・空行・配置は揃っているか。
- [ ] **Smell**: `tmp`、`data`、`retval`、曖昧な `Get`、否定的な真偽名、単位のない数値、`min`/`max` や範囲端点の意味が曖昧な名前。
- [ ] **Blocker の目安**: 名前や条件が実際の意味と異なり、誤用・誤読・境界値バグを招く。**Suggestion**: 意味は正しいが理解に余計な時間がかかる、または整形が不統一。
- [ ] **例外**: 短い局所スコープの慣用名、API・フレームワークの固定名、プロジェクトの既存命名規約を優先する。

## 2. ループとロジックの単純化

- [ ] **確認観点**: 正常系・関心の高いケースが自然な順序か。ガード節と早期 return/continue でネストを抑えられるか。条件式・三項演算子・ループの終了条件が追えるか。再代入とスコープは最小か。
- [ ] **Smell**: 深いネスト、否定の連鎖、巨大な式、制御フラグ、トリッキーな三項演算子、複雑な `do/while`、同じ値の散在、不要な中間状態。
- [ ] **Blocker の目安**: 条件の誤読、終了条件の誤り、未処理分岐、例外・境界値の見落としにつながる。**Suggestion**: 動作は追えるが説明変数や単純化で理解時間を下げられる。
- [ ] **例外**: パフォーマンスや言語イディオムが構造を要求する場合は、既存パターンと測定可能な理由を優先する。

## 3. コードの再編成

- [ ] **確認観点**: 1つの関数・ブロックが一度に1つの仕事をしているか。高レベルの流れと下位処理が分離され、関数境界が意図を示すか。既存の標準・成熟ライブラリを再利用できるか。
- [ ] **Smell**: 入力検証・取得・変換・副作用の混在、無関係なユーティリティの埋め込み、過剰な抽象化、同じ処理の重複、不要な車輪の再発明。
- [ ] **Blocker の目安**: 責務混在が誤った順序・副作用・再利用時の誤用を生む、または要件を隠す。**Suggestion**: 動作は正しいが分割・統合で流れを明確にできる。
- [ ] **例外**: 小さな処理の抽出で文脈が失われる場合、性能・トランザクション境界・公開APIを壊す場合は現状を優先する。

## 4. コメント

- [ ] **確認観点**: コメントがコードから自明でない Why、設計判断、制約、定数の根拠、落とし穴、境界条件を説明しているか。コードと現実に一致しているか。
- [ ] **Smell**: 処理を逐語訳するコメント、悪い命名を弁解するコメント、古い説明、重要な非自明制約の欠落。
- [ ] **Blocker の目安**: コメント不足により危険な制約・必須順序・境界条件が誤用される、またはコメントが実装と逆で誤解を誘発する。**Suggestion**: 自明なコメントを削除・意図コメントへ置換できる。
- [ ] **例外**: 公開API・法規制・運用手順・互換性のための定型文書は、プロジェクトの文書規約を優先する。

## 5. テストコード

- [ ] **確認観点**: テスト名から対象と状況が分かるか。入力と期待結果が短く対比できるか。データは意図が明快か。テストは独立し、失敗時に原因を追えるか。ヘルパーが核心を隠していないか。
- [ ] **Smell**: 巨大なセットアップ、曖昧なテスト名、マジックデータ、過剰なモック、共有状態、実装詳細だけを検証するテスト、境界・失敗系の欠落。
- [ ] **Blocker の目安**: テストが成功しても重要な要件・失敗経路を保証せず、回帰を見逃す。**Suggestion**: 仕様書としての読みやすさや失敗診断を改善できる。
- [ ] **例外**: テストフレームワークの慣用構文、既存の命名・fixture・parameterized test 規約、再現性や性能上の必要性を優先する。
