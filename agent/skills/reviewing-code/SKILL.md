# Reviewing Code

## 目的・適用条件

- コードを変更せず、他者が最短時間で理解できるか（Time-till-understanding）と、動作・要件・保守上のリスクを確認する。
- 対象は、ユーザーが示した差分、コミット、ファイル、関数、またはレビュー対象として明示された範囲に限る。
- 差分レビューでは変更範囲外のコードを、変更の影響を説明するために必要な場合を除き指摘しない。
- プロジェクトの規約、既存実装、言語イディオムを先に確認し、一般的な可読性原則より優先する。
- レビューと修正案の提示に徹する。ファイル編集、リファクタリング、コミット、ビルド、テスト実行は行わない。

## ワークフロー

1. **対象と境界を確定する。** 差分、関連する要件、変更目的、言語、対象範囲を確認する。不明なら推測せず質問する。
2. **規約と文脈を読む。** 対象ディレクトリの規約、近接する既存コード、公開API・呼び出し側・テストを必要最小限確認する。レビュー対象を広げる場合は理由を明示する。
3. **正しさを先に確認する。** 要件漏れ、境界値、エラー処理、状態・並行性、セキュリティ、API誤用、互換性のリスクを追跡する。
4. **可読性を確認する。** 命名、制御フロー、責務分離、コメント、テストを、Time-till-understanding の観点で点検する。
5. **観点を掘り下げる条件。** 命名・ロジック・構成・コメント・テストの可読性を詳しく確認するとき、また別のレビュー工程へ同じ観点基準を共有するときは、`references/readability-checklist.md` を読む。対象範囲と観測事実も併記する。
6. **重要度を判定する。** Blocker と Suggestion を区別し、確信のない nitpick は無理に指摘しない。重複する指摘はまとめる。
7. **出力を整える。** 各指摘に箇所、理由、具体的な修正案を付け、未確認事項と良かった点を必要に応じて添える。コードは変更しない。

## 判断基準・デフォルト方針

### 重要度

- **Blocker**: バグ、要件漏れ、誤用を招く危険な命名・論理、セキュリティ・データ損失・互換性などのリスク。対応しないとマージや利用を止めるべきもの。
- **Suggestion**: 可読性、理解コスト、保守性を改善する任意提案。動作上の問題がないもの。
- 単なる好みや細かな nitpick で Blocker を埋めない。

### 原則

- 行数の短縮や clever な書き方より、意図・前提・データの流れが速く理解できることを優先する。
- 名前は値の役割、単位、状態、境界を表し、広いスコープほど情報を持たせる。ただし既存の命名規約や言語イディオムを機械的に覆さない。
- 深いネスト、複雑な否定、巨大な式、不要な再代入は、ガード節、説明変数、責務分離で単純化できるか確認する。
- 1つの関数・ブロックに複数の無関係な仕事を混在させず、標準ライブラリや既存の成熟した抽象化を優先する。ただし変更範囲と等価性を確認してから提案する。
- コメントは自明な処理ではなく、設計理由、制約、落とし穴、境界条件を説明しているか確認する。
- テストは入力と期待結果が明快で、対象・状況を名前から理解でき、独立した仕様例になっているか確認する。既存のテスト命名規約を優先する。
- 修正案は最小限で、対象言語・既存API・副作用・境界条件を保つ。等価性や失敗時の挙動を確認できない案は断定せず、確認事項として出す。

## 出力フォーマット

```markdown
## Review

### Blocker
- `path/to/file:行` — **箇所**: 何が問題か。
  - **理由**: 理解コスト、バグ、要件漏れ、またはリスク。
  - **修正案**: どう直すか。必要なら条件・等価性・検証方法も示す。

### Suggestion
- `path/to/file:行` — **箇所**: 改善点。
  - **理由**: 読み手や保守への影響。
  - **修正案**: 実行可能な具体案。

### Summary
- Blocker: 件数 / Suggestion: 件数
- 未確認事項・前提:
- 良かった点（任意）:
```

Blocker がなければ「なし」と明記する。問題がなければ、無理に Suggestion を作らず「重大な指摘なし」と報告する。

## Gotchas

- 読み取り専用のレビューなのに、依頼者の承認なくファイルを編集したり、修正を適用したりしない。
- 差分範囲外の古い問題を、今回のレビュー結果として勝手に列挙しない。影響がある場合だけ、根拠と範囲を示す。
- 既存規約を無視し、`min_`、テスト命名、フォーマットなどの具体例を全言語・全プロジェクトへ機械的に押し付けない。
- 「分かりにくい」「改善した方がよい」のような抽象的指摘だけで終わらせず、箇所・理由・具体的な修正案を添える。
- 細かな nitpick を Blocker にして、バグや要件漏れなどの重要な指摘を埋もれさせない。
- 等価性、副作用、エラー処理、境界条件を確認せず、壊れるリファクタリング案を出さない。
- テストやビルドを実行していない場合、実行済みのように報告しない。レビュー結果と検証していない事項を分ける。

## 参照ファイル

- 命名・ループとロジック・再編成・コメント・テストの観点を掘り下げるときだけ、`references/readability-checklist.md` を読む。参照先から別のファイルは参照しない。
