# Architecture Review Checklist

設計案の自己点検または独立した設計レビュー時に、対象、前提、未確認事項とともにこの基準を使う。指摘は根拠と修正案を添え、好みをBlockerにしない。

## 判定軸

- **Blocker:** 要件・データ損失・整合性・セキュリティ・障害耐性・互換性を損ない、合意や実装を止める欠陥。必須の前提、SoR、冪等性、失敗時の経路、採用理由が欠落している場合も含む。
- **Suggestion:** 動作を直ちに壊さないが、理解、保守、運用、検証可能性を改善する提案。数値根拠の追加や図の明確化など。
- 不明な事実は断定せず「未確認」とする。重複指摘とnitpickを避け、例外条件を考慮する。

## 1. 要件・特性と過剰設計

- [ ] 目的、利用者、スコープ、成功指標、負荷、期限、既存制約、障害時の損失が明記されている。
- [ ] -ilities は少数に絞り、優先順位・SLO・測定方法・対象外がある。
- [ ] モノリス／モジュラーモノリス＋同期を比較の基準にしたか。分散、非同期、CDC、CQRSの要件根拠があるか。
- [ ] バサ号（将来の全要件を先取り）や、独立デプロイ以外の理由のないマイクロサービスがないか。
- [ ] **Smell:** 「高可用・高性能・高柔軟性をすべて最大化」「将来のため」のみでコストが説明されない。

## 2. 境界・分割・結合度

- [ ] 境界が業務ワークフロー、Actor/Action、変更単位、不変条件に対応し、責務と所有者が明確か。
- [ ] DBテーブルごとのCRUDマネージャ（エンティティ・トラップ）をドメイン境界と誤認していないか。
- [ ] 静的／動的コナーセンス、同期連鎖、共有状態、局所性を説明し、遠い境界ほど弱い契約にしているか。
- [ ] クアンタム数、デプロイ単位、異なるスケール・可用性要求が分散化を正当化しているか。
- [ ] **Smell:** 循環依存、共有DB、巨大な共通モジュール、機能変更が全レイヤーを横断する分割。

## 3. データシステム・整合性・冪等性

- [ ] SoR、所有権、派生データ、再構築方法、鮮度と削除伝播が明記されている。
- [ ] 直接Dual Writesや安易な2PC/XAを避け、CDC／イベント／補償の失敗経路を示しているか。
- [ ] リクエストIDが入口から永続化・メッセージ・消費まで渡り、重複排除とリトライが安全か。
- [ ] 整合性モデル（Read-after-write / Monotonic Reads / Consistent Prefix Reads）、許容遅延、古い読み取りのUI/API挙動が明記されている。
- [ ] **Smell:** 「最終的整合性」で済ませる、投影失敗・再構築・順序逆転を想定しない、キャッシュを真実として扱う。

## 4. 通信・スタイル・障害耐性

- [ ] 同期をデフォルトにし、非同期の必要性（バッファ、独立スケール、障害局所化等）が測れる形で説明されている。
- [ ] タイムアウト、再試行、バックオフ、サーキットブレーカ、Ack、DLQ、順序、消失、重複、部分障害を扱っている。
- [ ] レイヤード／マイクロカーネル／イベント駆動／マイクロサービスの選択が適用条件と運用コストに結び付いている。
- [ ] 観測性（相関ID、遅延、滞留、鮮度、エラー、再処理）と復旧手順がある。
- [ ] **Smell:** 非同期なら疎結合とだけ述べる、ネットワークを関数呼出し扱いする、メッセージ消失を無視する。

## 5. ADR・検証可能性

- [ ] 2〜3案を同じ軸で比較し、採用案のWhy、却下理由、再検討条件をADRに記録している。
- [ ] 前提、未決事項、残余リスク、合意者、停止条件が明記され、合意前に実装へ進まない。
- [ ] 適合度関数、アーキテクチャテスト、負荷・障害・整合性テスト、監視で構造劣化を検出できる。
- [ ] 移行・ロールバック・データ修復の計画があり、実行可能な検証手順になっている。
- [ ] **Smell:** HowだけでWhyがない、図と本文が矛盾する、検証不能な形容詞だけ、決定者が不明。

## 例外条件

- プロトタイプ、使い捨てツール、短命な移行スクリプトでは、将来の適合度関数や高い進化容易性を要求しない。ただし寿命、データ損失範囲、廃棄条件を明記する。
- 厳密な既存制約（外部API、規制、ベンダー製品、組織境界）がある場合、理想案を押し付けず、制約・残余リスク・緩和策をBlocker判定の根拠にする。
- 例外を認めてもSoR、データ損失防止、必要な整合性、リトライ安全性、合意前の実装停止を黙って省略しない。緊急時は期限と事後レビューを記録する。

## 出力テンプレート

```markdown
## Architecture Review
### Blocker
- `設計箇所` — 問題 / 根拠 / 修正案
### Suggestion
- `設計箇所` — 改善点 / 理由 / 具体案
### Summary
- Blocker: 件 / Suggestion: 件
- 未確認事項・前提:
- 合意待ちか、実装へ進める条件:
```
