# Creating Skill

Agent Skills 標準と OpenCode V2 の双方で移植可能なスキルを、実務で使える最小構成として作成する。

## 配置レイヤーを先に判定する

| 要求 | 適切な配置 | 判定理由 |
| --- | --- | --- |
| リポジトリ全体の常時ルール、禁止事項、共通方針 | `AGENTS.md` | すべての作業に適用する指示 |
| 明示的に呼び出す定型コマンド、引数付き操作 | `commands/` | コマンド名で実行する手順 |
| 専用の役割・人格・長時間の委任エージェント | `agents/` | エージェント定義と委任境界 |
| 再利用する専門知識・ワークフロー・判断基準 | `skills/` | 文脈に応じて発見・再利用する能力 |

`skills/` が適切でなければ、スキルを作らず該当レイヤーを提案する。

## 5フェーズ作成ワークフロー

### Phase 1: 実経験起点のヒアリングとスコープ確定

- [ ] 解決したい課題を、成果物と失敗コストを含めて一文で確認する。
- [ ] 典型的なユーザープロンプトを、表現ゆれを含めて2〜5件集める。
- [ ] 固有の前提、社内規約、ツール制約、頻出する落とし穴を聞き出す。
- [ ] 既存資料、過去の実タスク、レビュー指摘から再利用可能な知識を抽出する。
- [ ] 対象がスキルか、別の配置レイヤーかを再確認する。
- [ ] 配置先、利用者、移植性（Agent Skills 標準／OpenCode）を確定する。
- [ ] 単発回答や一般知識をスコープから除外する。

### Phase 2: 構成設計と合意

- [ ] スキルIDとディレクトリ構成案を提示し、合意を得る。
- [ ] `SKILL.md` には常時必要な手順だけ置き、詳細は Progressive Disclosure で分離する。
- [ ] 壊れやすい処理（形式、順序、検証、破壊的操作）は厳密に指定する。
- [ ] 柔軟な判断は Why と原則を示し、実装を過度に固定しない。
- [ ] 選択肢を羅列せず、デフォルト方針と例外条件を示す。
- [ ] 「なくてもできる一般論は削る」削減フィルタを各節に適用する。
- [ ] 参照ファイルの読込条件とツール実行条件を定め、特定エージェント名や委譲構成はオーケストレーター／`agents/` 側へ分離する。

### Phase 3: ドラフト作成

- [ ] `assets/SKILL.template.md` を雛形として使い、不要な節は削る。
- [ ] 仕様確認が必要なときは `references/specification.md` を読む。
- [ ] 発動条件や description を設計するときは `references/description-guide.md` を読む。
- [ ] frontmatter は標準フィールドを優先し、OpenCode 固有拡張は移植性とともに明記する。
- [ ] 本文は目的、適用条件、手順、判断基準、出力形式の順に整理する。
- [ ] `## Gotchas` は参照資料ではなく `SKILL.md` 本体に置く。
- [ ] 実在する相対参照だけを書き、参照チェーンを1階層に保つ。

### Phase 4: 機械検証とトリガー点検

- [ ] `sh <creating-skill-dir>/scripts/validate_skill.sh <target-skill-dir>` を実行する。
- [ ] エラーが0件になるまで、修正と再検証のループを行う。
- [ ] 行数、frontmatter、ID、description、参照ファイルを確認する。
- [ ] should-trigger を3〜5件提示する（明示／非明示、表現ゆれ、詳細度を混ぜる）。
- [ ] 隣接領域の near-miss を should-not-trigger として3〜5件提示する。
- [ ] 発動し過ぎる場合は description の境界を修正し、例示の単語暗記を避ける。

### Phase 5: 実タスク検証と反復改善

- [ ] 必要に応じて `references/eval-guide.md` を読み込む。
- [ ] 2〜3件のリアルタスクを選び、skill あり／なしを同じ条件で比較する。
- [ ] 各タスクに客観的なアサーションを設定し、根拠付きで採点する。
- [ ] 出力、手順の抜け、判断理由、トークン量、所要時間を確認する。
- [ ] トレースから不要な説明、誤発動、繰り返し失敗を特定する。
- [ ] Gotchas、手順、参照分割、description に反映して再検証する。

## 判断基準とデフォルト方針

1. まず再現可能な成果物を定義し、知識の網羅性より作業成功率を優先する。
2. 手順は最短の安全なデフォルトを示し、例外は条件と対応を隣接させる。
3. 外部ツールやネットワークに依存する場合は、依存条件と代替を明記する。
4. 削除・上書き・送信・権限変更は、対象と影響を確認してから扱う。
5. 一般的な説明は参照へ移すか削除し、失敗を防ぐ固有知識を本文に残す。

## 出力フォーマット

作成時は次を簡潔に報告する。

- 配置先とスキルID
- 作成・変更ファイル一覧
- should-trigger / should-not-trigger のテスト例
- 実行した検証コマンドと結果
- 未解決の前提、追加の実タスク検証

## ヒアリング用チェックリスト

作成依頼を受けたら、次の質問を必要な範囲で確認する。回答済みの項目は繰り返し聞かない。

- [ ] 最終的に誰が何を完成させるのか。
- [ ] 入力は何で、どの形式・サイズ・品質を想定するのか。
- [ ] 成功を何で判定し、失敗するとどんな手戻りが起きるのか。
- [ ] 既存のコマンド、規約、テンプレート、サンプルはあるか。
- [ ] 人間が必ず判断する箇所と、自動化できる箇所はどこか。
- [ ] 使ってよいツール、禁止された送信・変更、権限の境界は何か。
- [ ] 同じ課題がどの頻度で発生し、単発依頼ではない根拠は何か。
- [ ] ローカル環境だけで使うのか、他の Agent Skills 実装へ移植するのか。

情報が足りない場合は、仮定を隠さず「確認待ち」としてスコープを狭くする。曖昧なまま長い手順を書き始めない。

## スキルIDと構成の決め方

ID は利用者が意図を表現する名詞または短い動作名にする。既存スキルとの衝突を確認し、略語やベンダー名は本当に必要な場合だけ使う。

初期構成は次を基準にする。

```text
<skill-id>/
├── SKILL.md
├── references/   # 条件付きで読む長い仕様・例
├── assets/       # コピーして使う素材・テンプレート
└── scripts/      # 決定的で繰り返す検査・変換
```

新しいファイルを増やす前に、それが本文の可読性、正確性、再利用性のどれを改善するかを一文で説明する。説明できないファイルは作らない。

## Progressive Disclosure の配置ルール

- メタデータ：発動判断に必要な成果と境界だけ。
- `SKILL.md`：最初に読む目的、デフォルト手順、停止条件、出力形式。
- `references/`：仕様表、背景説明、長い例、評価方法。
- `assets/`：モデルが解釈するより、そのまま複製・編集する方が安全な素材。
- `scripts/`：入力と出力が明確で、毎回同じ処理をする機械的な作業。

本文から参照を読む条件は、手順の直前に書く。「必要なら読む」だけでは条件にならないため、「frontmatter の互換性を判断するとき」など観測可能な条件にする。

## 制御度のキャリブレーション

手順ごとに、失敗時の損失と判断の可逆性を確認する。

| 状態 | 書き方 |
| --- | --- |
| 破壊的・不可逆・形式依存 | コマンド、順序、確認条件を厳密に指定 |
| 成果物の品質に直結 | 必須条件、検証方法、停止条件を指定 |
| 複数の妥当解がある | デフォルトを一つ示し、例外の選び方を説明 |
| 文脈依存の判断 | Why と判断軸を示し、具体値は固定しない |

細かい擬似コードでモデルの判断を覆い尽くさない。逆に、壊れやすい手順を「適切に処理する」とだけ書かない。

## 受け入れレビュー

初稿ができたら、作成者以外の観点で次を点検する。

- [ ] description だけを読んで、発動範囲を説明できる。
- [ ] 本文を上から読めば、最初の安全な一歩が分かる。
- [ ] 成功条件と終了条件が出力形式に反映されている。
- [ ] 条件付き資料を読まなくても、通常ケースは完了できる。
- [ ] 参照資料を読めば、例外ケースの判断を再現できる。
- [ ] 失敗時に無言で続行せず、確認または停止する箇所がある。
- [ ] 特定エージェント名やマルチエージェント構成のハードコードがなく、環境依存のツール名・パスには互換性の注記がある。
- [ ] 既存の一般ルールと重複せず、このスキル固有の価値がある。

## トリガー境界の作り方

should-trigger は、単にスキル名を含む文だけにしない。次のように意図を保ったまま表現を変える。

1. 明示依頼：「この作業用のスキルを作って」
2. 非明示依頼：「毎週同じ手順でレビューしているので再利用したい」
3. 背景付き依頼：「過去の失敗を防ぐため、チーム向けに標準化したい」
4. 境界付近：「この手順を一度だけ実行して結果を教えて」では単発なので除外する。

should-not-trigger は、同じ語彙でも成果物が異なるケースにする。たとえばスキル作成と、既存スキルを使った単発実行、AGENTS.md の規約変更、専用エージェントの設計を分ける。

## 変更時の安全手順

既存スキルを改修する場合は、先に対象の `SKILL.md` と参照先を読み、変更範囲を列挙する。本文、参照、検証スクリプトを同時に変える場合は、各変更の理由を記録する。

- [ ] 既存の発動例と除外例を保存する。
- [ ] 変更後に frontmatter と参照パスを機械検証する。
- [ ] 変更前後の実タスク結果を比較する。
- [ ] 改善が発動率だけでなく成果物品質にも効いたか確認する。
- [ ] 不要になった節や資料を削除し、古い指示を残さない。

## Gotchas

- 一般論を長く書くと、重要な固有手順が埋もれ、コンテキストも浪費する。
- `description` が「役立つときに使う」のように曖昧だと、発動漏れと誤発動が増える。
- `references/` を作るだけで読込条件を書き忘れると、モデルは重要資料を読まない。
- `SKILL.md` の大文字小文字、ディレクトリ名、`name` の不一致は発見や検証を壊す。
- 参照から参照を読む2階層以上のチェーンは、読み込み漏れと追跡困難を生む。
- 固有ツール設定やローカルのエージェント名・委譲構成を無自覚に混ぜると、移植性と保守性を失う。
- 選択肢の羅列は判断を遅くする。デフォルトと例外を先に置く。
- サンプルの単語だけでトリガーを調整すると、未知の表現に弱い過学習になる。

## 同梱リソースの使い分け

| リソース | 読む／実行する条件 |
| --- | --- |
| `references/specification.md` | 標準仕様、frontmatter、発見パス、移植性を確認するとき |
| `references/description-guide.md` | description、発動境界、テストクエリを設計・修正するとき |
| `references/eval-guide.md` | 実タスク比較、アサーション、採点、トレース分析を行うとき |
| `assets/SKILL.template.md` | 新規 `SKILL.md` の初稿を書き始めるとき |
| `scripts/validate_skill.sh` | 初稿後、変更後、提出前に機械検証するとき |

参照資料は必要なフェーズでのみ読み、不要な一般論を本文へ戻さない。作成対象の検証には必ず対象ディレクトリを引数に渡す。
