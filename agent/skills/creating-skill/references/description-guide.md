# description 設計ガイド

## 4原則

1. エージェントへの明確な発動指示として書く（例：「〜するときに使用する」「Use this skill when...」）。
2. スキルの機能ではなく、ユーザーの意図と達成したい結果から書く。
3. 明示的にスキル名を言わない依頼でも発動する条件と、発動しない境界を明記する。
4. 1024文字以内で、固有語を詰め込み過ぎず簡潔にする。

## 対比例

良い例：`CSVの売上データを集計・検証し、再現可能なレポートを作成する。売上集計や月次レポートを依頼されたときに使い、単発の数値回答やデータ入力だけには使わない。`

悪い例：`データ関連で役立つスキル。必要なら使う。`

良い例は意図、成果、非明示ケース、境界を含む。悪い例は発動条件も除外条件も観測できない。

## トリガー検証クエリ

should-trigger は4軸を混ぜて4〜8件作る。

- 表現ゆれ：同義語、略語、口語、別の文順。
- 明示度：スキル名を言う依頼／言わない依頼。
- 詳細度：短い依頼／背景と制約を含む依頼。
- 複雑さ：単純な典型例／複数段階の実務例。

should-not-trigger は必ず隣接領域の near-miss にする。無関係な質問ではなく、似た語を含むが成果物や意図が異なる依頼を3〜5件用意する。

## 過学習を避ける

クエリは train 60%、validation 40% に分ける。train の失敗を直したら、validation で未知の言い回しと境界を確認する。失敗クエリの単語を description に足すだけでなく、概念・目的・除外条件の境界を修正する。改善のたびに分割を固定して比較する。
