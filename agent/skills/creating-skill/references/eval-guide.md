# 実タスク評価ガイド

## ケース設計

まず2〜3件で開始する。`evals/evals.json` の最小例：

```json
{
  "skill_name": "example",
  "evals": [
    {
      "id": "monthly-01",
      "prompt": "実際の依頼文",
      "expected_output": "合計値と入力エラーを含むレポート",
      "files": [],
      "assertions": [
        "成果物に合計値がある",
        "入力エラーを明示する"
      ]
    }
  ]
}
```

ケースは実際の文脈、入力形式、制約を含め、正常系だけでなく境界値・欠損・曖昧な指示を1件以上入れる。

## 比較手順

各ケースをクリーンなコンテキストで実行し、with_skill と without_skill を比較する。既存スキルの改修なら old_skill と new_skill を同じ条件で比較する。プロンプト、入力、モデル、ツール権限を固定し、出力とログを保存する。

## アサーション

客観的で検証可能、かつ表現に脆すぎない条件にする。「正しい」ではなく、必須フィールド、検算可能な値、エラー時の停止、根拠の提示などを書く。各条件に根拠を添えて PASS/FAIL を採点し、部分達成は理由を記録する。

## 診断と改善

- 両方PASS：スキルの差分価値が薄い。一般論を削り、固有の失敗防止に絞る。
- 両方FAIL：スキル外の前提、入力、ツール権限を確認し、目的を再定義する。
- ばらつき大：曖昧な指示やトリガー境界を特定し、Why とデフォルトを補う。
- トークン／時間の外れ値：冗長な参照や不要な手順を削り、繰り返し処理はスクリプト化する。

人間レビューで実用性、説明責任、保守性を確認する。結果を一般化して反映し、スキルをスリム化し、必要な箇所では Why を説明する。改善後は同じケースを再実行し、回帰を確認する。
