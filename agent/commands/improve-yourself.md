# improve-yourself

パーソナルAIパートナーチームの自己改善を行ってください。

## 確認対象ファイル

実行時に以下のファイルのすべてを読み込むこと。

`~/dotfiles/agent/`
- `opencode.jsonc`: opencodeの設定ファイル
- `AGENTS.md`: 全エージェントの役割定義
- `agents/*.body.md`: 各エージェントの役割定義
- `agents/*/*.frontmatter.md`: 各エージェントのメタデータ
- `commands/*.md`: 頻繁に利用するプロンプト
- `skills/*.md`: エージェントのスキル
- `logs/frictions/*.md`: 未処理の摩擦ログ群（セッション単位。未記録時は存在しない）
- `logs/improve.md`: 当作業により適用した改善ログ

※ 注意事項

`agents/*/dist/*.md`ファイルは、 `agents/*.body.md` と `agents/*/*.frontmatter.md` を連結して生成されたビルドファイルです。
改善の際には生成物を直接編集せず、 `agents/*.body.md` と `agents/*/*.frontmatter.md` を改修するようにしてください。

## 業務フロー

1. 確認対象を読み込む。
2. 確認対象ファイルを精査し、以下の観点で分析を行う。
    - 改善ログに記載の内容が再発していないか
    - 摩擦ログに記載の内容に要改善と思われるログはあるか
    - 各摩擦ログの「資材断面」と改善ログの「適用時ベース断面」を照合し、改善適用前の古い断面で発生した事象は再発扱いせず除外する（必要に応じて `git -C ~/dotfiles merge-base --is-ancestor` 等で確認）
3. 分析結果をもとに、摩擦ログの内容を`要改善` | `改善不要` | `様子見`に分類する。
4. `要改善`の摩擦に対する改善提案は、再発防止効果や影響範囲などを踏まえて最も効果的と思われる最大3件までに絞ってユーザーに提示し、返答に応じてファイル編集を行う（複数の摩擦ログを1つの根本原因に統合して1提案としてもよい）。今回の提案に含めなかった`要改善`項目は次回へ持ち越す。
5. ファイルのクリーニングを行う。
    - 3で改善ログへの書き込みから30日以上再発していない（= `logs/frictions/*.md` に同事象が発生していない）ログについては、改善ログから削除する。
    - 4で`改善不要`としたログおよび4でユーザーから`改善不要`と言われた事象については、該当する`logs/frictions/*.md`から関連記録を削除する。
    - 4で解決策を講じたものについては、該当する`logs/frictions/*.md`から関連記録を削除し、改善ログにその内容を記録する。事象一覧が空になった`logs/frictions/*.md`ファイル自体は削除する（`様子見`・今回提案を持ち越した`要改善`・ユーザーが保留とした項目が残る場合はファイルに残す）。
6. 完了報告及び、利用ツールに応じて agent 定義ファイルの再ビルドを依頼するようユーザーに返答する。

## 分析と設計原則

- **構造的パターンの抽出（局所最適の禁止）**
    - 単発の特殊なミスに対して個別具体的なルール（「～の時は～しない」の羅列）を追加しない。
    - 複数のログに共通する**根本原因（ルーティング基準の曖昧さ、責務の重複、承認粒度のズレ）**を抽象化して簡潔な原則に落とし込む。
- **1-IN, 1-OUT**
    - プロンプトが長くなるほどLLMの指示遵守率は低下する。
    - 新しいルールを追加する場合は、**既存の冗長な表現・形骸化したルール・重複記述の削除や統合**をセットで提案し、全体の行数を現状維持～削減することを目指す。
- **適切な配置レイヤーの選定**
    - 全員が守るべき安全・連携ルール -> `AGENTS.md`
    - 振り分け・確認タイミング・応答テンポ -> `agents/chief.body.md`
    - 特定の専門作業の質 -> 該当するサブエージェントの`agents/*.body.md`ファイル
    - 特定環境・特定ツールの固有知識 -> プロンプト本体ではなく別ファイル等への外部化を提案
- **構成変更の検討**
    - 特定のエージェントがほとんど呼ばれていない、または逆に常に直列で呼ばれてオーバーヘッドになっている場合、役割の統廃合や起動条件の変更も提案する。
    - AIパートナーチーム内での対応改善ループが回せていない場合にもサブエージェントの追加・削減や役割変更を提案する。
- **提案数の上限（最大3件）**
    - ユーザーのレビュー負担を抑え質の高い改善に集中するため、1回の実行で提示する改善提案は最も効果的と思われる最大3件（再発頻度・影響範囲・根本解決への寄与度で優先順位付け）に絞る。残りの`要改善`項目はログに残して次回に持ち越す。
- **勝手な上書きの禁止**
    - まずは**提案（diff出力）のみ**を行い、ユーザーの承認を得てから実際の編集を行う。

## 出力フォーマット

### 分析結果と改善提案

改善提案は効果が高い順に最大3件まで記載すること。

```markdown
### 1. ログ分析サマリー

- 改善対象パターン:
    - blah-blah-blah（例: ルーティング過剰、手戻りが発生、やり直しが発生etc.）
    - etc.
- 次回に持ち越す項目:
    - ${`要改善`だが提案上限（3件）を超えたため次回へ持ち越す内容と理由}
    - etc.
- 見送った項目:
    - ${`改善不要` / `様子見`とした内容と理由}
    - etc.

### 2. 改善提案

#### 提案1: [${タイトル}]（対象: `${ファイル名}`）

- **狙い**: ${何の課題を解消するのか}
- **行数変化**: +X行/-Y行
${diff}

#### 提案2: [${タイトル}]（対象: `${ファイル名}`）
#### 提案3: [${タイトル}]（対象: `${ファイル名}`）

```

### 改善ログ

```markdown
#### [${タイトル}]（対象: `${ファイル名}`）

- **適用日**: ${YYYY-MM-DD}
- **適用時ベース断面**: `${適用開始時点で git -C ~/dotfiles rev-parse HEAD により取得したコミットハッシュ}`
- **狙い**: ${何の課題を解消するのか}
- **行数変化**: +X行/-Y行

${diff}

#### [${タイトル}]（対象: `${ファイル名}`）

...（適用した数だけ繰り返す）
```
